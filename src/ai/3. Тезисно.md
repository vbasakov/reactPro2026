# Тезисно

**Цель**
Освоить продвинутые инструменты Redux Toolkit для работы с асинхронными запросами. Познакомиться с redux-thunk и RTK Query. Понять, когда какой подход применять.

## Почему важно?

Почти каждое приложение работает с сервером: загрузка данных, обновление, удаление. Без грамотной архитектуры асинхронность может стать источником:

-
дублирующихся fetch-запросов — например, при каждом переходе на страницу заново загружается один и тот же список;

-
утечек запросов — пользователь покинул страницу, но запрос все еще в процессе и может обновить состояние уже несуществующего компонента;

-
ручной синхронизации — после удаления объекта нужно самому обновлять список или делать повторный запрос.

RTK Query решает проблемы «из коробки»:

-
кеширует результат и переиспользует его, если он актуален — повторные запросы не делаются без необходимости;

-
отменяет незавершенные запросы, если компонент размонтировался;

-
инвалидирует и обновляет связанные данные автоматически после мутаций (invalidatesTags), без ручного dispatch.

Запросы становятся предсказуемыми, а код — чище и устойчивее.
Выбор подхода напрямую влияет на читаемость, поддержку и масштабируемость приложения.

## Как работает Redux?

Redux — библиотека для управления состоянием в JavaScript-приложениях. Она построена на принципе однонаправленного потока данных.

**Основные сущности**

-
Store — единое хранилище состояния приложения.

-
Action — простой объект { type: string, payload?: any }, описывающий, что произошло.

-
Reducer — чистая функция (state, action) => newState, обновляющая состояние на основе действия.

-
Dispatch — способ отправить действие в Redux.

#### Поток данных:

1.
Компонент вызывает dispatch(action).

2.
Action попадает в middleware (если подключены).

3.
Middleware могут обработать или изменить действие (или даже не передать дальше).

4.
Затем действие обрабатывается **reducer**, которые обновляют состояние.

5.
Компоненты, подписанные на нужные части состояния, получают обновления.

#### **Middleware: что это и зачем нужно?**

Middleware — расширения между dispatch и reducer, которые позволяют:

-
выполнять асинхронный код;

-
логировать действия;

-
выполнять условную логику;

-
диспатчить дополнительные действия.

Пример:

```
// Пример обычного action
dispatch({ type: 'tasks/add', payload: newTask })
// Пример thunk
dispatch(async (dispatch, getState) => {
const data = await fetch('/api/tasks')
dispatch({ type: 'tasks/set', payload: data })
})
```

**Пример. Подключение middleware: до / после.**

До: базовая конфигурация хранилища

```
import { configureStore } from '@reduxjs/toolkit';
import tasksReducer from './tasksSlice';
export const store = configureStore({
reducer: {
tasks: tasksReducer,
},
});
```

После: подключаем logger middleware

```
import { configureStore } from '@reduxjs/toolkit';
import logger from 'redux-logger';
import tasksReducer from './tasksSlice';
export const store = configureStore({
reducer: {
tasks: tasksReducer,
},
middleware: (getDefaultMiddleware) =>
getDefaultMiddleware().concat(logger),
});
```

**Пример жизненного цикла действия:**

```

Component → dispatch(action)

          → middleware (логика, API-запросы, условия)

          → reducer (создание нового state)

          → Store обновлен → Component обновляется

```

#### **Что важно понять?**

-
Reducer никогда не делает асинхронных операций — только чистая синхронная логика.

-
Middleware нужен, чтобы обрабатывать «эффекты» (API, таймеры, маршрутизация и прочее).

-
Это позволяет отделить бизнес-логику от UI и централизовать поведение.

#### Пример: эволюция Redux

Vanilla Redux (много шаблонного кода):

```
// action
const ADD_TODO = 'ADD_TODO';
const addTodo = (text) => ({ type: ADD_TODO, payload: text });
// reducer
function todosReducer(state = [], action) {
switch (action.type) {
case ADD_TODO:
return [...state, action.payload];
default:
return state;
}
}
// store
const store = createStore(todosReducer);
```

Redux Toolkit (меньше кода, декларативный API):

```
import { createSlice, configureStore } from '@reduxjs/toolkit';
const todosSlice = createSlice({
name: 'todos',
initialState: [],
reducers: {
add: (state, action) => {
state.push(action.payload);
},
},
});
export const { add } = todosSlice.actions;
const store = configureStore({
reducer: { todos: todosSlice.reducer },
});
```

## Подходы к работе с асинхронностью

**1. Redux Thunk**

Redux Thunk — middleware, который позволяет диспатчить функции вместо обычных объектов. Такие функции могут выполнять асинхронные операции (например, fetch) и после завершения — диспатчить реальные действия.

**Что делает thunk?**

-
Откладывает выполнение действия, пока не завершится асинхронный код.

-
Позволяет диспатчить несколько действий последовательно (например, loading → success).

-
Дает доступ к dispatch и getState прямо внутри функции.

**Пример «ручного» thunk:**

```
export const loadTasks = () => async (dispatch, getState) => {
dispatch({ type: 'tasks/loading' });
try {
const res = await fetch('/api/tasks');
const data = await res.json();
dispatch({ type: 'tasks/loaded', payload: data });
} catch (e) {
dispatch({ type: 'tasks/error', error: e.message });
}
};
```

Этот подход полезен, но требует много шаблонного кода: loading, try/catch, dispatch результатов и так далее.

**Упрощение с createAsyncThunk (из Redux Toolkit)**

createAsyncThunk — функция из Redux Toolkit, которая автоматически генерирует три состояния:

-
pending

-
fulfilled

-
rejected

и избавляет от ручного шаблонного кода.

Пример:

```
import { createAsyncThunk } from '@reduxjs/toolkit';
export const fetchTasks = createAsyncThunk(
'tasks/fetch',
async () => {
const res = await fetch('/api/tasks');
return await res.json();
}
);
```

**Как работает?**

1.
Вызывается dispatch(fetchTasks()).

2.
Redux Toolkit автоматически диспатчит tasks/fetch/pending.

3.
Если промис успешен — tasks/fetch/fulfilled.

4.
Если произошла ошибка — tasks/fetch/rejected.

Эти состояния можно обрабатывать в slice с помощью extraReducers:

```
builder
.addCase(fetchTasks.pending, (state) => {
state.status = 'loading';
})
.addCase(fetchTasks.fulfilled, (state, action) => {
state.status = 'succeeded';
state.tasks = action.payload;
})
.addCase(fetchTasks.rejected, (state, action) => {
state.status = 'failed';
state.error = action.error.message;
});
```

**Когда использовать Redux Thunk?**

**✔ Подходит**

-
У вас простая логика (например, загрузка списка или сохранение формы).

-
Нужна понятная ручная обработка состояний: loading, error, data.

-
Вы хотите минимальный инструмент без дополнительных зависимостей.

**❌ Не подходит**

-
Нужно обрабатывать много этапов, отменять запросы, ждать другие экшены.

**Резюме**

| Что | Описание |
| --- | --- |
| Что делает | Позволяет запускать асинхронные действия с доступом к dispatch и getState |
| Упрощает | Создание логики «загрузка → успех → ошибка» через createAsyncThunk |
| Плюсы | Простота, предсказуемость, хорошая интеграция с Redux Toolkit |
| Минусы | Не очень удобен для сложных сценариев (цепочки, отмена, параллелизм) |

**2. Redux Saga**

Redux Saga — middleware для Redux, которое использует генераторы (function*) и концепцию «саг» (процедур) для управления побочными эффектами: асинхронными запросами, задержками, отменами и так далее.

Saga предоставляет более декларативный и управляемый подход к побочным эффектам по сравнению с thunk.

**Что делает Redux Saga?**

-
Позволяет легко создавать сложные потоки: цепочки запросов, параллельные вызовы, отмену задач.

-
Упрощает тестирование побочных эффектов — каждый шаг описан явно.

-
Делит бизнес-логику и API-запросы на отдельные процессы, которые можно запускать и контролировать.

Пример: загрузка задач через сагу

```
// watcher — наблюдает за действиями
function* watchLoadTasks() {
yield takeEvery('tasks/load', fetchTasksSaga);
}
// worker — выполняет побочный эффект
function* fetchTasksSaga() {
try {
yield put({ type: 'tasks/loading' });
const response = yield call(fetch, '/api/tasks');
const data = yield call([response, 'json']);
yield put({ type: 'tasks/success', payload: data });
} catch (error) {
yield put({ type: 'tasks/error', error: error.message });
}
}
```

Подключение:

```
import createSagaMiddleware from 'redux-saga';
import { configureStore } from '@reduxjs/toolkit';
import rootSaga from './sagas';
const sagaMiddleware = createSagaMiddleware();
const store = configureStore({
reducer: { tasks: tasksReducer },
middleware: (getDefaultMiddleware) =>
getDefaultMiddleware({ thunk: false }).concat(sagaMiddleware),
});
sagaMiddleware.run(rootSaga);
```

**Когда использовать Redux Saga?**

**✔ Подходит**

-
Нужен тонкий контроль над побочными эффектами: отмена, задержки, race conditions.

-
Нужно отделить побочные эффекты от компонентов и slice.

-
В проекте есть многоэтапные операции или зависимости между запросами.

**❌ Не подходит**

-
У вас простое приложение с базовыми API-запросами.

-
Хочется минимального кода без использования генераторов и дополнительного boilerplate.

**Почему удобно?**

| Возможность | Redux Saga |
| --- | --- |
| Сложные цепочки эффектов | ✅ Простая реализация через генераторы |
| Отмена / race conditions | ✅ Поддержка race, cancel, takeLatest |
| Логика вне компонентов | ✅ Саги — отдельные функции |
| Тестирование побочных эффектов | ✅ Декларативная структура легко тестируется |

Redux Saga — идеальный выбор для проектов, где асинхронная логика сложная и ее нужно  гибко контролировать и отделять от UI.

**3. RTK Query**

RTK Query — мощный инструмент из Redux Toolkit, который позволяет автоматически создавать API-клиент прямо внутри Redux. Он берет на себя всю рутину: отправку запросов, управление статусами, кеширование и повторные вызовы — без лишнего кода и ручных действий.

**Что умеет RTK Query?**

-
Генерирует кастомные хуки (useGetTasksQuery, useAddTaskMutation и так далее).

-
Управляет кешем автоматически.

-
Обрабатывает загрузку, ошибки, успехи.

-
Позволяет конфигурировать запросы: заголовки, авторизация, инвалидация данных.

-
Сильно сокращает количество кода.

Пример: получение задач

| slice | RTK Query |
| --- | --- |
| import { createSlice, createAsyncThunk } from '@reduxjs/toolkit';<br>export const fetchTasks = createAsyncThunk('tasks/fetch', async () => {<br>const res = await fetch('/api/tasks');<br>return res.json();<br>});<br>const tasksSlice = createSlice({<br>name: 'tasks',<br>initialState: { tasks: [], status: 'idle', error: null },<br>reducers: {},<br>extraReducers: (builder) => {<br>builder<br>.addCase(fetchTasks.pending, (state) => {<br>state.status = 'loading';<br>})<br>.addCase(fetchTasks.fulfilled, (state, action) => {<br>state.status = 'succeeded';<br>state.tasks = action.payload;<br>})<br>.addCase(fetchTasks.rejected, (state, action) => {<br>state.status = 'failed';<br>state.error = action.error.message;<br>});<br>},<br>}); | import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';<br>export const api = createApi({<br>reducerPath: 'api',<br>baseQuery: fetchBaseQuery({ baseUrl: '/api' }),<br>endpoints: (build) => ({<br>getTasks: build.query<Task[], void>({<br>query: () => 'tasks',<br>}),<br>}),<br>}); |

Использование в компоненте:

| slice | RTK Query |
| --- | --- |
| const dispatch = useDispatch();<br>const { tasks, status } = useSelector(state => state.tasks);<br>useEffect(() => {<br>dispatch(fetchTasks());<br>}, []); | const { data: tasks, isLoading, error } = useGetTasksQuery(); |

**Что делает автоматически?**

-
Отправляет GET /api/tasks.

-
Устанавливает флаги isLoading, isError, isSuccess.

-
Кеширует результат и переиспользует его, пока он валиден.

-
Перезапрашивает данные при изменении аргументов или инвалидации.

**providesTags и invalidatesTags**

Это система тегов, которая позволяет RTK Query автоматически управлять кешированием и повторными запросами.

Представьте:

-
у вас есть список задач (/tasks);

-
вы добавили или удалили задачу (POST, DELETE);

-
RTK Query должен понять: «Ага, список задач устарел — надо перезапросить».

RTK Query работает с двумя типами тегов:

| Механизм | Что делает |
| --- | --- |
| providesTags | Говорит: «Этот запрос возвращает данные с этим тегом» |
| invalidatesTags | Говорит: «Этот мутационный запрос делает указанный тег устаревшим» |

Когда тег становится «устаревшим», RTK Query автоматически перезапрашивает все запросы, которые его предоставляли (providesTags).

Пример: после добавления новой задачи — обновить список.

```
endpoints: (build) => ({
getTasks: build.query<Task[], void>({
query: () => 'tasks',
providesTags: ['Tasks'],
}),
addTask: build.mutation<void, NewTask>({
query: (newTask) => ({
url: 'tasks',
method: 'POST',
body: newTask,
}),
invalidatesTags: ['Tasks'],
}),
});
```

**Что происходит в примере?**

-
getTasks делает GET /tasks и сообщает RTK Query: *«Я предоставляю тег **Tasks**»*.

-
addTask делает POST /tasks и сообщает: *«Я меняю данные, связанные с тегом **Tasks**, — обнови их!»*

-
RTK Query автоматически вызывает getTasks заново — кеш обновляется.

**Почему важно?**

-
Не нужно вручную вызывать refetch — кеш обновляется сам.

-
Минимум багов, связанных с устаревшими данными в UI.

-
Предсказуемое поведение: добавили задачу → список обновился.

-
Масштабируемо: легко описывать зависимости даже между разными частями API.

**Когда и зачем использовать теги?**

| Сценарий | Нужно ли использовать теги? |
| --- | --- |
| Загрузка списка с возможным изменением | ✅ Да, providesTags + invalidatesTags |
| Загрузка одного ресурса (детальная карточка) | ✅ Да, providesTags: (result) => [{ type: 'Item', id }] |
| Постоянно изменяющиеся данные (чат, лог) | ⚠ Можно использовать polling или WebSocket вместо тегов |

**Когда использовать RTK Query?**

**✔ Подходит**

-
Вы работаете с типичным REST API (GET, POST, PUT, DELETE).

-
Нужно быстро настроить API-клиент без вручную прописанных thunk.

-
Нужна стабильная система кеширования и обновления данных.

**❌ Не подходит**

-
Вам нужно делать многоэтапные цепочки запросов.

-
Требуется тонкий контроль над побочными эффектами (например, отмена запросов, debounce, race conditions).

-
Вы работаете с нестандартным API, который сложно описать декларативно.

**Почему удобно?**

| Возможность | RTK Query |
| --- | --- |
| Генерация хуков | ✅ Автоматически (useXYZQuery) |
| Кеширование | ✅ Из коробки |
| Повторные вызовы | ✅ Через refetch или auto polling |
| Обработка ошибок | ✅ Через isError и error.message |
| Инвалидация / обновление | ✅ Через providesTags / invalidatesTags |

RTK Query — отличный выбор для 80–90 % API-задач. Он позволяет сосредоточиться на бизнес-логике, а не на ручной обработке загрузок, ошибок и кеша.

## Redux Thunk vs RTK Query

| Критерий | RTK Query | Redux Thunk (createAsyncThunk) |
| --- | --- | --- |
| Подход | Декларативный, описывается createApi и endpoints | Императивный, пишется логика вручную в thunk |
| Генерация хуков | ✅ Автоматически (useGetXQuery, useAddXMutation) | ❌ Нужно подключать вручную в компонент |
| Загрузка / ошибка / успех | ✅ Доступны флаги isLoading, isError, isSuccess | ❌ Нужно реализовывать вручную через extraReducers |
| Кеширование данных | ✅ Из коробки, с автообновлением и инвалидацией | ❌ Нужно реализовывать вручную |
| Автоподгрузка / polling | ✅ Есть встроенный polling и refetchOnFocus | ❌ Требует ручной реализации |
| Количество кода | Минимальное (все в одном месте) | Больше шаблонного кода (thunk + slice + состояние загрузки или  ошибки) |
| Гибкость и контроль | ⚠ Подходит для стандартных CRUD сценариев | ✅ Гибкий, можно реализовать любую логику, в том числе цепочки, отмену |
| Работа с нестандартным API | ⚠ Иногда сложно обойти ограничения baseQuery, требует кастомизации | ✅ Полный контроль: можно писать любой код |
| Обновление / инвалидация данных | ✅ Через providesTags и invalidatesTags | ❌ Только вручную |
| Сложные сценарии (race, debounce, wait) | ❌ Не поддерживается из коробки | ✅ Можно реализовать вручную |

## Альтернативы Redux Toolkit

Redux Toolkit — мощный и универсальный инструмент, но не единственно возможный. В зависимости от задач, размера проекта и команды вы можете рассмотреть другие решения для управления состоянием.

Ниже — краткий обзор популярных альтернатив.

| Библиотека | Особенности и плюсы | Когда стоит использовать |
| --- | --- | --- |
| MobX | Реактивная модель, минимальный код, автоматические обновления | Маленькие и средние проекты, быстрые прототипы |
| Recoil | Гибкое управление атомами и селекторами, глубоко интегрирован с React | Если нужно дерево состояний с разделяемыми атомами |
| Zustand | Простая и легкая альтернатива Redux с очень лаконичным API | Малые проекты, локальное состояние, удобен для hooks |
| Rematch | Обертка над Redux с упрощенным синтаксисом и встроенными эффектами | Проекты, где хочется Redux-подход, но проще |
